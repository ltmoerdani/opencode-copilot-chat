## Overview

Follow-up triage to PR #288 (issues #282–#287) covering five reports from the same user. Four were classified as upstream behaviour, model-generated arguments, or long-standing design debt; one was a real gap in this extension: Gemini 4 Hydrogen on Zen failed on follow-up turns because opaque `thoughtSignature` values were dropped from the response and never replayed. This document records the verdicts, the fix, and the open follow-ups.

## Root cause — Gemini thought signatures

Google's `generateContent` API has no dedicated thought blocks. Signatures are metadata attached to parts: a thought part, a `functionCall` part, or the trailing empty-text part of a response. The official `Part.thoughtSignature` field is documented as "an opaque signature for the thought so it can be reused in subsequent requests", and `Candidate.finishReason` includes `MISSING_THOUGHT_SIGNATURE` ("Request has at least one thought signature missing"). In stateless mode the client must resend thought blocks exactly as received.

Our Google normalizers flattened parts into OpenAI-style text/reasoning/tool-call fields and discarded every other part property. A signature-only event (`{"text":"","thoughtSignature":"…"}`) was even classified as empty and returned `{ choices: [] }`. The next turn therefore went out without the signature and Gemini 4 rejected it.

## Fix

The signature now makes a full round-trip without ever becoming visible chat text:

1. `core/routing.ts` — `normalizeGoogleStreamEvent()` and `normalizeGoogleFullResponse()` collect non-empty `thoughtSignature` values into `thought_signatures` on the normalized delta/message. A signature-only event is no longer treated as empty.
2. `transports/google.ts` + `transports/extractors.ts` — the Google adapter captures signatures across SSE events and emits one internal transcript part after the stream.
3. `chatParts.ts` — new `application/vnd.opencode.thought-signature+json` data part (same invisible seam as the reasoning marker), capped by `MAX_THOUGHT_SIGNATURES` in `config.ts`.
4. `provider/messages.ts` — `convertMessage()` reads the part back into `ApiMessage.thought_signatures`; `normalizeMessages()` concatenates signatures when adjacent assistant messages merge, so history trimming cannot silently drop them.
5. `request/google.ts` — replays each signature as a trailing `{ text: "", thoughtSignature }` part on the `model` turn, matching the shape the gateway returned. Tool-call turns keep their `functionCall` parts ahead of the signature parts.

No other transport is affected: the field is only read by the Google request builder.

## Verification

- `npm run compile` — clean.
- `src/test/google-thought-signature.test.ts` — 11/11 pass: stream and full-response normalization, signature-only event, transcript round-trip and malformed payloads, replay on plain and tool-call turns, no extra parts when no signature was received, and history normalization retaining/merging signatures.
- Live Gemini 4 Hydrogen verification in Copilot Chat is still pending (requires the reporter's Zen key / harness).

## Open follow-ups

- **Haiku 5.5 compaction** — upstream VS Code #336797. Nothing to change here; the extension already advertises the correct 1M window. Recheck when the upstream issue closes.
- **`globalState` growth** — migrate `opencodego.usageLog.v1.<key>` from `globalState` to `globalStorageUri`, keeping only a small index in `globalState`. Separate change with its own migration/compat plan; deliberately not bundled into this fix.
- **`gpt-6.2-sol` skill loader** — no extension change. If a raw tool schema from Copilot shows our payload altering `server`/`uri`, reopen with that evidence.
